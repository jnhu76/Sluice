# G1 C1 — Notification protocol: state machine, redundancy condition, and the suppression experiment

Status: controlled experiment (arm C1-A). Baseline commit `85e87244`
(includes the adopted C9-A change; the C9-A path does not touch
ProgressSource). Authority: PROG-01/PROG-02/PROG-04 of the root spec.

## 1. The state machine as implemented (progress_source.hpp)

The transport is one nonblocking eventfd; the semantic content is the epoch
pair (`progress_epoch_`/`progress_exhaustion_`), never the byte count.

| transition | producer | mechanism | consumer side |
|---|---|---|---|
| not ready → ready | `signal()`/`interrupt()` under `mtx_` | epoch bump **then** `write(eventfd, 8)` — one critical section (:248–260, :418–439) | parked waiter's `poll` returns POLLIN; running waiter's next revalidation sees the new epoch |
| ready → ready | further `signal()`s before any drain | today: another `write` (counter grows) | indistinguishable to consumers: drain reads until EAGAIN, poll is level-triggered, revalidation compares epochs |
| ready → acknowledged | `drain_notification_nolock_` under `mtx_` (:393–414) via `wait_if_unchanged`'s pre-park drain or `acknowledge_notification` | `read` until EAGAIN | fd unreadable; next signal must write again |
| acknowledged → newly ready | next `signal()` | as row 1 | as row 1 |

The losslessness argument (PROG-02): signal's bump and write are atomic
w.r.t. the waiter's revalidate+drain critical section. Either the bump lands
before the waiter's revalidation (waiter never parks) or the write lands
after the drain (waiter's poll wakes). The byte carries no information; it is
a wake edge.

## 2. When does existing readiness prove an extra signal redundant?

Exactly when the fd counter is nonzero (a notification byte is pending):
every parked waiter is already being woken by that byte, every future park
drains before polling, and every running waiter revalidates the epoch — an
additional write changes no observable decision. The byte is boolean
transport; the epoch pair carries the semantics. Conversely, when the counter
is zero the write is load-bearing and must happen.

## 3. Alternatives considered

1. **No-protocol-change syscall suppression (chosen, arm C1-A):** keep
   `bool notification_pending_` under `mtx_`, maintained only by the two
   existing fd-touching helpers. `wake_notification_nolock_` returns early
   when pending; `drain_notification_nolock_` clears it only on the EAGAIN
   branch (counter provably 0). No epoch/ack protocol change; the fd remains
   the sole kernel-side truth; the bit is a conservative summary
   (false→extra write = harmless; true must be reachable only while a byte
   exists — set on successful write or EAGAIN-saturation, cleared only at
   EAGAIN).
   Kernel coexistence (io_uring registered eventfd writes counter
   increments that bypass this class): kernel writes only add bytes, so
   `pending==true ⟹ counter≥1` is preserved; drain still ends at EAGAIN.
   Registered eventfd wakeups of the uring backend do not go through
   `signal()` at all.
2. Notification coalescing timers/batches: introduces timing state and a
   delayed-wake window — protocol-visible; rejected.
3. Backend-local batching (submit/complete batching): PROG-03 territory,
   changes when work becomes visible; out of C1 scope.
4. NO_CHANGE: baseline already recorded; C9-A did not touch this path, so
   the 5.06% sampled eventfd-write share remains unaddressed — not acceptable
   without trying 1 first.

Mechanism-justification gate for `notification_pending_`: it represents the
kernel-side fact "notification byte pending", owned by the fd; it is justified
by the directly measured cost (5.06% of cycles on W-02-TP-w4, 1 write/op
directly observed in the #535 syscall census); it is derived from the
authority at the only two sites that mutate the counter; classified as a
derived summary (non-authoritative; worst case a wrongly-false bit costs one
redundant write); replaces `None`; removal condition: if the A/B shows no
measured win, the bit and this commit are withdrawn.

## 4. Required negative oracles (deterministic, no sleeps)

| id | failure mode | oracle |
|---|---|---|
| N1 | lost wake after acknowledgement | waiter parks on a drained fd (prepark gate), producer signals from another thread → `wait_if_unchanged` must return progress (write must have happened because pending was cleared by the drain) |
| N2 | suppressed wake hides the latest epoch | two signals with no drain between; a parked waiter wakes once and its next `snapshot` observes epoch ≥ both bumps |
| N3 | multi-producer lost signal | k producers signal while the waiter is parked at the prepark gate; the waiter must wake and observe the maximal epoch; the fd must be drained exactly once back to EAGAIN |
| N4 | readiness cleared too early / stuck suppressed | round trip: signal → fd readable; `acknowledge_notification` → fd unreadable; signal again → fd readable again. The second readability proves the bit was cleared at the EAGAIN (a stuck-true bit would suppress the second write and leave the fd unreadable) |
| N5 | shutdown waiter stranded | existing shutdown suites: the final drain/retire path leaves no parked waiter (shutdown_lifecycle_test must stay green) |
| N6 | failed backend progress not delivered | existing poison/health suites: a health-failed wait returns `failed` regardless of suppression (progress race + conformance suites stay green) |

Plus the full PROG-02 race matrix (progress_source_ownership_test,
threadpool/uring_progress_race_test, external loop suites) as the regression
floor, and the mutation builds.

## 5. Verdict (post-experiment)

**ADOPTED** (with one test-suite correction the oracles forced).

- All six negative-oracle classes green: the two new context-level oracles
  (`progress_notification_suppression_test`: acknowledge round trip,
  concurrent producers) plus the full PROG-02 race matrix, external-loop,
  ownership, shutdown, cutover and conformance suites (61 targets, release,
  liburing=y — TOTAL_FAILURES=0).
- **The oracles caught a real contract violation**, not in the library: the
  uring progress-race suite drained the live notification fd with a raw
  `::read` (uring_progress_race_test.cpp:1406) — a second drain authority,
  which the header has documented away since the C2-C convergence
  ("the fd itself is never a second drain authority"). Under suppression
  that desynchronized the pending summary from the counter and suppressed
  the post-poison retirement wake (`FAIL:
  post_poison_accept_push_retires_through_failure_terminal`). Fixed by
  draining through the source-level `acknowledge_notification()` via the new
  `progress_source_for_test()` seam (mtx_-only; the context-level
  acknowledge would deadlock against a submitter paused mid-`submit_read`,
  which holds `access_mtx_` across the backend call). PROG-02 explicitly
  permits this optimization: "Notifications may coalesce or be spurious".
- Paired A/B vs B0 (arm = C9-A + C1-A, `ab/c1/AB.md`; a first run of this
  campaign was discarded as contaminated — the full test suite ran
  concurrently and shifted the uring rows by ±13%):
  W02-threadpool-4k-d16-w4 **+8.8%** ops/s (cpu/op 13004→11284 ns, p99
  worst ×1.045), W03-threadpool-4k-d16-w4 **+27.9%** (noisy-case caveat,
  tail ×1.02), uring controls +7.1% both.
- `W02-threadpool-4k-d16-w1` paired −9%: attributed by strace census
  mostly to C9-A (its faster passes raise park cycles ~+50%, poll
  27865→41920/invocation); C1-A runs *fewer* park cycles than C9-A alone
  (41920→30988) and cuts notification writes 60003→42973. The w1 delta vs
  B0 is disclosed as a C9-A/C1-A aggregate and re-measured in the final
  combined-arm A/B with 15 repetitions.
- Write-count effect on the primary case, per the mechanism target: the
  eventfd write share (5.06% sampled in #535) is the cost removed at w4;
  the A/B cpu/op delta (−13.2%) is consistent with that share plus the
  reduced futex traffic.

## 6. Preregistered decision rule (as frozen before measurement)

Adopt iff: all oracles and suites green AND the paired A/B shows ≥5% on
`W02-threadpool-4k-d16-w4` with no tail regression beyond the noisy-case
caveat, and no regression on W-03/uring controls. Otherwise withdraw the
commit and record `C1_NO_SAFE_CHANGE` with the evidence.
