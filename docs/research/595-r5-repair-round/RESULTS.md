## Answers to the three questions

**Q1 — can #630's diagnostic and analysis methods be repaired to
usable/reviewable?** YES for the instrument, NO for formal attribution.
The v1 races are confirmed, fixed (v2 per-writer instrument,
`research-595-r5rm-diag` @ `61bf73d6` + post-round quiesce-breach safety
`492086ac`) and validated (TSan-clean on a 5-thread synthetic harness —
v1 reports races under the same harness — and the real io_uring bench;
full 20000/20000 join on every event kind; the fixed analyzer's failure
handling has 4/4 deterministic counterexamples). The analysis-method
errors (F2 percentile-contribution rule, F4 semantics wording, F6
archive gaps) are corrected. But the repaired instrument STILL fails the
frozen ±3pp on/off perturbation window (interactions −4.9/+5.4pp on
d16, +5.1/+9.2pp on d4; CIs span up to ±23pp) — so diagnostic numbers
stay lead-level and `TRACE_READY` holds for the instrument while
**formal tail attribution remains NOT_ESTABLISHED**.

**Q2 — does C1/C2 cleanup actually reduce CPU work and improve p99 vs
R_original?** Not established on the main shape; small raw savings at
d4/d2serial that exceed the cross-binary band but are not formally
separated from it. On MAIN the raw C−R p99 effect is −1.77% with 95%
upper bound −0.55% < 0 ("established" by the frozen criterion), BUT the
A0-original/A0-cleanup calibration shows a same-order binary-layout
effect (p99 −1.47%), so the p99 gain is within the calibration band and
is **not attributed to the cleanup logic**. C−R CPU on MAIN is −0.73%
[−2.02,+0.50] — not established. At W03-d4/d2serial the raw C−R CPU
savings (−3.86%/−4.42%) exceed the calibration point estimates
(−1.49%/−2.28%) — consistent with small real savings, but the
calibration is a same-path binary effect with no joint-uncertainty
model, so this stays an observation, not an estimate. On W02 cells C−R
is positive (+3.2% cpu) with calibration +2.1/+3.4% — no cleanup harm
or gain demonstrated. **Scope caveat:** "CPU" everywhere is
process-rusage CPU/op; kernel io-wq worker CPU is outside rusage
(ticks recorded separately, R/C ≤ A0) — this is not a whole-system CPU
number. Keeping C1/C2 rests on the source-level justification (removes
a duplicate scan, 18-scenario byte-identical equivalence), not on a
proven universal performance win.

**Q3 — does R_cleanup meet the full gate vs A0?** NO — same single
failure as R4, robustly: MAIN-W03-D16 process-rusage CPU/op −22.09%
[−22.75,−21.41] (PASS), throughput +28.49% (one-sided lower +27.53% ≥
−3%, PASS), p95 +1.15% (upper95 +3.66% ≤ +5%, PASS), **p99 +17.97%
(upper95 +20.34% > +5%, FAIL; Holm-adjusted p = 1.0)**. Protections:
W03-d4 PASSES every protection bound (C better than A0 on all four
metrics); **W03-d2serial FAILs on throughput/p95/p99 — its CPU item
PASSES** (point +3.90%, upper95 +4.90 ≤ +5%; the first published table
wrongly failed it by testing the main-gate CPU threshold and quoting the
two-sided CI upper); W02-d1 and W02-d2 FAIL (cpu upper95 +5.9/+6.3,
tput lower −5.6/−5.9, p95 upper +5.5/+5.8, p99 upper +5.8/+9.1). The
shallow-queue tax persists under cleanup, as expected from proven
equivalence; note d2serial degrades with almost no batching, which
indicates an adapter/call-path tax component — the tax is a property of
the R-family adapter path as a whole (cleanup-invariant), and
"batching-inherent" is NOT established by this round.
