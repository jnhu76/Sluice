# F4 — 尾延迟保护（仅实测块）

**图**：`F4_tail_guardrails.svg` / `.png`；数据：`figure-data/F4_tail_effects.csv`。

**任务与平台**：同 F2/F4 各块自身协议（24 对 AB/BA 或 A/A，WARMUP=1 MEASURED=5，
warm tmpfs，`taskset -c 2`）。**臂与树**：三个 R2 同 SHA 配对块（B_R2−A_R2，
二进制 `32beabcd…`）与两个 A/A 参照块（灰）。**样本数**：每块 n=24 对。
**误差条**：bootstrap 10,000（seed 5950）百分位 95% CI；**方向**：negative = 候选臂
延迟更低（改善）；红色虚线为预注册非劣界 +5%（延迟恶化侧），−5% 仅为对称参考，
不是门。**单位**：%。p50/p95/p99 为运行级聚合（invocation 内 5 个 measured rep 的
百分位均值，再按 24 配对做统计）；未保留同口径逐请求延迟，故无 ECDF/CCDF 附图。

**主要发现**：唯一测到的尾延迟恶化是**旧 B_R2 在 W-02 D2**（p50 +2.29%、p95 +5.23%、
p99 +7.05%，p95/p99 单侧上界越 +5% 界）；同一旧策略在 W-02 D3/D16 反而显著改善
尾延迟（p95/p99 至 −32%），说明退化是**形状特异**而非全局。两个 A/A 块的尾延迟
半宽 0.43–2.34 pp，环境噪声底足够小。**R3 B 侧的全部保护单元（D1、64 KiB、
threadpool、SMT/跨物理、饱和）NOT RUN**（semanticsReady 未翻转），无法判断新算法
的尾延迟代价——这是本轮最重要的未覆盖项。
