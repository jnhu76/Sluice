That foundation remains useful, but the long-term optimization program must be **workload-driven** rather than API-, backend-, or microbenchmark-driven.\n\n> **We will optimize for different real I/O workload regimes. A common semantic foundation does not imply a universal fastest execution path.**\n\nThe question is no longer only \"how much does one read/write cost?\" It is:\n\n> For a specific workload, what data movement, synchronization, ownership transition, metadata work, kernel interaction, and physical I/O are *actually necessary*—and which costs can be removed, overlapped, batched, deferred, or relocated while preserving the workload's observable contract?\n\nThis is a **long-lived strategic research umbrella and decision ledger**, not a new implementation roadmap or permission to expand the v2 public API. Design principles\n\n1. **Workload first, mechanism second.** Freeze the operation/dependency graph, correctness and durability oracles, resource budget, workload distribution, and baseline *before* selecting optimizations.\n2. **Minimum necessary work, not minimum code.** Eliminating entire operations, redundant copies, repeated metadata work, unnecessary barriers and serial dependencies takes precedence over shaving instructions off work that need not exist.\n3. **Common semantics, specialized paths.** Preserve the shared File/Request contract where applicable; permit workload-specific internal mechanisms or standalone experiments when justified. Never force a universal fast path.\n4. **Separate authority from residency.** Logical ownership, read/write permissions, physical buffer lifetime, DMA/OS borrow obligations, version publication, and reclamation authority are distinct. Moving an owner/handle does not imply moving bytes; a copy does not by itself transfer exclusive ownership.\n5. **Space is a resource budget, not a free win.** Preallocation, double buffering, immutable sharing, COW, version retention and delayed reclamation are candidates. Account for allocation, pinning, cache/NUMA traffic, fragmentation, memory footprint, and reclaim lag.\n6. **Copy is not always wrong.** Compare actual copy, no-copy handoff, shared immutable representation, remap/reflink/COW when legal, asynchronous copy overlapped with computation, and direct data movement. Security/isolation, replication, transformation and durability can *require* new bytes.\n7. **Drive-layer escalation is earned.** Test layout/algorithm, user-space I/O and io_uring bottlenecks before exploring user-space block/NVMe, polling, SPDK, P2P DMA or GPU paths. No user-space filesystem or driver is assumed to be the product destination.\n8. **No hero-cell generalization.** Keep negative regimes and crossover thresholds visible. An optimization may belong to one workload family and be harmful elsewhere.\n\n## 2. Workload portfolio (initial, extensible)\n\n| Family | Representative operation / real consumer | Likely cost hypotheses to test | Correctness / resource oracle |\n| --- | --- | --- | --- |\n| **W-A Streaming / transform / copy** | Sequential scan, copy/hash/filter, read → transform → write; Sluice apps | Buffer handoff, multiple buffers, overlap, allocation, cache traffic, copies | Identical bytes/output; bounded in-flight data; short I/O, failure and teardown |\n| **W-B Small random / latency-critical** | 4–16 KiB positional read/write, hot-set/skew, depth 1..N | Fixed call and queue costs, batching, locality, scheduling, tail | Same offsets/results/effects; achieved depth; p99 under load |\n| **W-C Durable append / WAL** | Append → commit/flush → recover, group commit | Barrier placement, syscall count, batching, buffer lifetime | Explicit durability and ACK ordering; crash/recovery correctness; RPO assumptions |\n| **W-D KV / LSM / DB execution** | Point/range read, immutable segment, compaction, DuckDB/fio admission | Repeated decode, materialization, read amplification, extents/rewrite, prefetch | Query/output oracle, version visibility, recovery, actual I/O exposure |\n| **W-E Object / immutable segments** | MinIO-style object/segment GET/PUT, metadata+data, large chunk streaming | Metadata colocation, lazy decode, reuse of serialized form, chunk pipeline | Version/object semantics, checksums, consistency, space overhead |\n| **W-F Accelerator/storage offload (conditional)** | KV cache offload, SSD ↔ GPU transfers, batch completion | Host control path, queue overhead, P2P DMA, registration, completion dependencies | Device capabilities, DMA lifetime, isolation, batch/dependency correctness |\n\nThe portfolio is a **hypothesis set**, not evidence that all regimes need bespoke optimization or that Sluice should implement object, KV, WAL or GPU storage APIs. Required workload sheet before each experiment\n\nEach child study must freeze:\n\n- **Consumer and semantics:** actual program/trace, logical operations, dependency DAG, ordering, visibility, partial effects, cancellation, required durability, failure and recovery behavior.\n- **Input envelope:** size distribution, read/write ratio, offsets, skew/hot set, arrival pattern, queue depth/in-flight bytes, concurrency, dataset size, warm/cold/cache and storage regime.\n- **Resource envelope:** RAM/pinned bytes, buffer count, workers, CPU/NUMA/SMT, device, filesystem, runtime/backend, hardware capabilities.\n- **Necessary-work hypothesis:** minimum bytes physically crossing each boundary; which copies, allocations, waits, syscalls, submissions, lookups or cache lines are semantically necessary, uncertain, or redundant. Cross-workload mechanism questions (research, not feature authorizations)\n\n**M1 — Ownership and data movement.** Can metadata/handle handoff replace payload relocation? What guarantees retain old buffers across asynchronous I/O, cancellation, reordering or teardown? Does immutable sharing or COW save real work, or only add reference-count/reclaim overhead?\n\n**M2 — Space-for-overlap.** When do preallocated pools, double/multi-buffering, version retention and delayed reclaim hide real waits? Identify the memory budget and crossover where space costs dominate.\n\n**M3 — Layout and representation.** Do inline small-object metadata, cached summaries, lazy decoding, serialized reuse, immutable extents, extent-level remapping or fewer materializations remove more work than changing the I/O invocation path?\n\n**M4 — Execution and I/O shape.** When do batching, coalescing, vectored I/O, prefetch, ordered vs independent completion, io_uring submission policy, or background compaction/flush reduce physical work?
