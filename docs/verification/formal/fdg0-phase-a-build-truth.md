# FDG-0 Phase A — Xmake Build Truth

> **Status: issue #298 Phase A (Build Truth), awaiting adversarial human
> review.** Phase B (semantic disposition / refresh workflow) and Phase C
> (AST fingerprint / enforcement) are explicitly **not** started. The
> machine-readable evidence record is
> [docs/results/formal/fdg0-phase-a.json](../../results/formal/fdg0-phase-a.json).
> This is NOT a production gate: it is not wired into
> `scripts/gates/pre-push.sh` or CI, and it does not modify any formal
> claim, TLA+ model, bridge test, or production C++ semantic.

## 1. Why #300's `src/` filter was insufficient

The merged #300 pilot selected the "production" SCIP surface with:

```python
src_entries = [e for e in compile_commands if e["file"].startswith("src/")]
```

That is a path prefix, not build truth. Measured consequences on the real
`compile_commands.json` (418 entries, 323 unique files, xmake 3.0.9+HEAD):

- The same TU appears under **multiple targets with different compile
  interpretations**: `src/async/uring_backend.cpp` had 9 entries — the
  production `sluice_async` entry, the `sluice_async_internal_testing`
  entry (`-DSLUICE_ASYNC_INTERNAL_TESTING`, extra include dirs), and the
  `uring_*` test targets' direct compiles. The `src/` filter admitted ALL
  of them, so the "production" graph contained **test-seam macro variants
  of production TUs** and scip-clang merged them additively.
- `src/experimental/*.cpp` (owned by `sluice_experimental_uring`, outside
  the formalized world) entered the graph merely because of its path.
- Nothing verified that the filtered set matched what Xmake actually
  resolves; a TU silently absent from the compdb was invisible to the
  filter and the experiment believed it had indexed a world it had not.

## 2. The T7 lesson

The #300 corrective-1 T7 fixture injected the moved TU by **cloning a
compile_commands entry by hand**; corrective-0's clone went into the
filtered compdb and never reached scip-clang while the experiment believed
it had. The lesson: compile-database provenance must be *regenerated by
the build system*, and the pipeline must prove the join, not assume it.
Phase A's T7-A specimen (§7) is the real end-to-end version: the move
happens through the Xmake source graph, `compile_commands.json` is
regenerated by `xmake project -k compile_commands`, and every hop is
recorded as evidence. No manual compile-database injection exists anywhere
in the Phase-A pipeline or specimens.

## 3. Xmake as Build Truth

New authority chain (implemented in `scripts/formal/build_truth.py`, no
regex parsing of `xmake.lua`):

```text
Xmake configured project
    -> xmake show -t <target> --format=json       declared target facts
    -> xmake lua (core.project API)               RESOLVED source membership
    -> xmake show --info=depgraph --format=json   dependency closure
    -> compile_commands.json                      per-TU compiler interpretation
    -> Build Manifest (build/formal-impact/build-manifest.json)
    -> selected compile_commands entries -> SCIP index -> formal-impact graph
```

Machine-readable interfaces verified on the installed xmake
(`v3.0.9+HEAD.2b184e1`):

| Fact | Interface | Notes |
| --- | --- | --- |
| Target kind / deps / defines / includedirs / compiler flags | `xmake show -t X --format=json` | `files` are UNRESOLVED globs |
| Resolved source membership | `xmake lua` + `target:sourcebatches()` | xmake's own glob expansion; new files under a glob are seen without reconfigure (verified) |
| Dependency closure | `xmake show --info=depgraph --format=json` | `{root_targets, targets:[{name,deps}]}` |
| Configured option state | `xmake lua` + `core.project.config` `config.load()` | `with-liburing` etc. |
| Per-TU compile command | `compile_commands.json` | duplicate entries per target; owning target encoded in the `-o` object path `build/.objs/<target>/...` (verified on 100% of 418 entries) |

The **owning-target join** is the load-bearing discovery of Phase A: the
`-o` object path gives a deterministic, Xmake-derived key from target
membership to compile_commands entries. No define-diffing heuristics are
needed.

## 4. Build Manifest schema

`build/formal-impact/build-manifest.json` (gitignored, rebuildable from
current HEAD + current Xmake configuration + selected worlds; schema
**sluice-build-manifest/1**):

```text
schema / schema_version / generated_at
head_sha
xmake_version
config: { id, options }              # fixed declared option list
build_id                             # deterministic sha256 (see §5)
worlds: [ one live world ]
  id / root_targets / dependency_closure / config
  targets: { name: { kind, direct_deps, defines, includedirs,
                     source_globs, resolved_sources, compiler, compiler_flags } }
  tus: { path: { owning_targets, compdb_identity, compiler,
                 defines, includes, flags } }
  compdb: { path, total_entries, selected_entries }   # DIAGNOSTICS ONLY:
                                                      # excluded from build_id
provenance: { BUILD: ... }
```

Every selected TU carries an exact `compdb_identity` (sha256 of the full
compile command) and its `owning_targets` — the exact join key set for that
TU (corrective-1 C4). There is no second hand-maintained source list:
expected lists appear only inside small hermetic fixtures; production
membership authority is Xmake output (§15 of #298).

## 5. Build identity

`build_id` is a deterministic sha256 over the SEMANTIC projection of the
manifest: schema, HEAD SHA, xmake version, config identity (option state),
and, per world: the selected targets, dependency closure, TU set with
`owning_targets`, and per-TU compile interpretation. It changes when any
relevant build interpretation changes — including `xmake f
--with-liburing=y` vs `=n` under the SAME HEAD (verified: different
`build_id`, A9).

The world's `compdb` cardinality block (`total_entries` /
`selected_entries`) is deliberately EXCLUDED from `build_id`
(corrective-1 C5): an unrelated test entry appearing in or disappearing
from `compile_commands.json` is a diagnostics change, not a change of the
production build world (regression CR7).

The graph records its build identity:

```json
"build": { "build_id": ..., "world_id": "sluice_async-liburing", ... }
```

`impact` and `check` verify graph ↔ manifest ↔ current Xmake configuration;
a mismatch is `BUILD_WORLD_CHANGED` / `BUILD_GRAPH_STALE` and fails closed
(never a silent `NO_FORMAL_IMPACT`).

## 6. Selected production variants

The first formalized production root is `sluice_async` with dependency
closure `[sluice_async, sluice_core]` (what Xmake actually reports — no
assumed closure). Explicitly excluded: `sluice_async_internal_testing`,
tests, bench, examples, fuzz, apps, research probes, and
`sluice_experimental_uring` (its sources stay out even though they live
under `src/`).

Config-gated production code is represented explicitly. The current
machine's configuration is `--with-liburing=y`, so the live world is:

```text
variant: id sluice_async-liburing, with-liburing: true
```

and the stub world (`sluice_async-default`, `with-liburing: false`) is a
distinguishable build identity (A9). No configuration matrix framework was
built; one live world per manifest is the minimum representation.

## 7. T7-A — the real Xmake E2E move

The #300 T7 specimen proved only SCIP cross-TU symbol-identity
survivability under a hand-injected compdb entry. T7-A proves the real
pipeline:

```text
Xmake source graph change (new TU appears under src/async/*.cpp)
  -> xmake project -k compile_commands   (regeneration, not injection)
  -> Build Manifest sees the new TU (owning_targets: [sluice_async])
  -> SCIP indexes the new TU
  -> anchor F03 ThreadPoolBackend::run_syscall resolves at the new TU
     (check reports def-site drift to the new TU,
     src/async/threadpool_run_syscall.cpp — a specimen path, restored
     byte-for-byte after the run)
  -> impact on the move patch != NO_FORMAL_IMPACT (F03 surfaces)
```

The specimen (threadpool_backend.cpp → new
src/async/threadpool_run_syscall.cpp, a transient specimen TU) is applied
to the working tree, indexed, verified, and restored byte-for-byte.
`compile_commands.json` is touched only by
`xmake project -k compile_commands`. Evidence is recorded per hop in
`docs/results/formal/fdg0-phase-a.json` (A7).

## 8. Config-gated anchors (F03 / liburing)

The F03 uring anchor (`UringAsyncBackend::finalize_operation_terminal_`,
declared `config_gate: SLUICE_HAS_LIBURING` in `spec/formal/anchors.json`)
is resolved under the `sluice_async-liburing` world: the selected TU
carries `-DSLUICE_HAS_LIBURING`, scip-clang indexes the real implementation,
and `check` reports it `OK` (A11). Under the stub world the same anchor is
a declared config-gated gap (WARN), unchanged from #300. The build world —
not a per-anchor heuristic — now explains which variant produced the graph
(`graph.build.world_id`).

## 9. Fail-closed behavior

New fail-closed states (all exit non-zero; `impact` exit 1, tooling hard
errors exit 2):

```text
UNKNOWN_BUILD_WORLD        Xmake-owned TU missing a compile_commands entry
                           owned by one of ITS owning targets (C4: a
                           sibling/dependency target's entry for the same
                           path is never borrowed), or the current world
                           cannot be computed, or the graph has NO build
                           identity block (C1)
ambiguous TU command       incompatible duplicate compile commands, no
                           deterministic Xmake-derived choice
BUILD_WORLD_CHANGED        manifest/graph identity != current Xmake config
                           (C3: fails closed even with NO changed C++ file)
BUILD_GRAPH_STALE          graph build_id != manifest build_id
UNKNOWN_BUILD_MANIFEST     manifest missing/malformed
```

`index` regenerates `compile_commands.json` first (killing the stale-compdb
class entirely), then fails closed on any join gap. `check`/`impact` never
regenerate; they verify.

Corrective-1 hardening (PR #302 review):

- **C1 — legacy graphs fail closed.** A graph without a build identity
  block (schema /1 or synthetic) is `UNKNOWN_BUILD_WORLD`: default `check`
  and `impact` exit non-zero. `--allow-legacy-graph-for-eval` is the
  explicit evaluation-only opt-in for historical fixtures; it is reported
  in the output (`LEGACY GRAPH ACCEPTED FOR EVAL` /
  `build_world_eval_skipped`) and never bypasses a FAILED verification —
  only a missing identity block.
- **C2 — build verification precedes `NO_FORMAL_IMPACT`.** `impact` checks
  the build world BEFORE the empty-diff short-circuit: with a drifted
  config, even `impact --range HEAD..HEAD` answers
  `UNKNOWN_FORMAL_IMPACT` / `BUILD_WORLD_CHANGED` with exit 1 (CR4, real
  machine). `NO_FORMAL_IMPACT` requires a verified build world AND no
  impact.
- **C3 — no `cxx_changed` escape hatch.** A build-world mismatch fails
  closed unconditionally: config-only or membership-only drift with a
  docs-only or empty diff is still a wrong-world analysis (CR5).
- **C6 — ownership parses `-o`, not the command text.** The owning target
  comes from the entry's `-o` object path located as an exact `-o`
  argument (shell-tokenized for `command`-string entries); `-o` missing,
  ambiguous, or outside the known `build/.objs/<target>/` layout makes the
  owner unknown (fail closed). An `-I` path that happens to contain
  `/.objs/<fake>/` never decides ownership (CR8).

## 11. Explicit non-goals (Phase A)

No Formal Facets / subclaims; no `correspondence.lock`; no semantic
refresh/disposition workflow (`semantic_disposition` stays `UNDETERMINED` —
Xmake Build Truth answers *what is built under which compile
interpretation*, never *what TLA+ action this code corresponds to*); no
AST fingerprint / LibTooling / CodeQL / tree-sitter; no graph database;
no daemon; no embedding/BM25; no historical gold corpus; no LLM
auto-clear; no pre-push or CI enforcement; no new TLA+/GenMC claims; no
production C++ semantic changes.

## 12. Residuals for Phase B/C

1. **Build-world verification cost.** `impact`/`check` re-query Xmake
   (~0.3 s) to recompute the current identity; acceptable for a manual
   tool, not for a hot gate.
2. **One live world per manifest.** Multi-world manifests (default +
   liburing side by side) were deliberately not built; Phase B may need
   them if a diff must be assessed against every production variant.
3. **`-o` path join is xmake-shape-dependent.** The `build/.objs/<target>/`
   join key was verified on this repo's xmake; a future xmake layout change
   must re-verify `build_truth.compdb_owner` (a self-test asserts the
   parser).
4. **SCIP graph granularity unchanged.** Anchor granularity,
   nearest-preceding attribution (HEURISTIC) and function-pointer thunk
   gaps remain exactly as documented in the #300 pilot (§7 of
   `formal-impact-pilot.md`).
5. **`git diff` untracked-file visibility.** The diff layer still cannot
   see untracked files; T7-A's impact query works around it with a
   `git diff --no-index` specimen patch (same mechanism as T8). A staged
   file is visible to `--working-tree` as before.
